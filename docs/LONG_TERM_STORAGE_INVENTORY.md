## Measured capacity signals

- AI-Foundation application-support tree: ~406 MiB at measurement time; ~385 MiB is the LibreChat tree.
- `llama-swap.log` is already ~19 MiB and is the clearest Foundation-adjacent append-only file observed.
- Mongo diagnostic capture was ~118 MiB at the original sample. Later live engine inspection proves a 250 MB diagnostic-directory ceiling and 10 MB file ceiling. The earlier ~3.6 GiB/year extrapolation is superseded and must not be used as an unbounded-growth forecast.
- Docker host state is materially larger than Foundation data: images ~39.33 GiB plus build cache ~11.52 GiB and volumes ~3.0 GiB. Reclaimability reported by Docker does not establish that Foundation may safely delete it.
- ToolHive persistence is now physically identified at `~/Library/Application Support/toolhive` (~2.1 MiB); its Foundation filesystem log is already ~1.1 MiB and has no Foundation-owned rotation proof.
- Meilisearch is a bind mount (~120 KiB now); pgvector is `librechat_pgdata2` (~48.3 MiB). Hatchet currently has active config/pgdata volumes (~6.5 KiB/~79 MiB) plus unlinked legacy Hatchet volumes (~74 MiB/0 B), which are not safe to delete until ownership/recovery proof is complete.

## LT02 capacity rule

No annual projection is fabricated for request-dependent stores without an operation rate. Instead each such surface must be tested using bytes/operation from accelerated workload and at least low/nominal/high operation-rate scenarios. Fixed-rate evidence (for example observed diagnostic/log growth) may be extrapolated but must be labelled as an observation-derived scenario, not a guarantee.

## 2026-09-21 lifecycle policy consolidation

`storage_lifecycle.py` now owns read-only lifecycle classification only. It deliberately does not delete Docker, ToolHive, llama-swap, model-cache, search/index, or other externally owned state. Owner-specific mutation remains in RetentionService, AttachmentCleanupLoop, backup/update code, and future external-owner adapters. This prevents a generic storage cleaner from becoming a second authority.

Live SQLite inspection: `guard.db` uses WAL and currently has a 0-byte WAL with `quick_check=ok`; the other canonical Foundation SQLite files currently use DELETE journal mode. All sampled DBs have `auto_vacuum=NONE`, zero freelist pages at the sample, and `quick_check=ok`. This is observation only; LT04 still requires accelerated churn/checkpoint/page-reuse/crash tests before policy changes.

Live host observations: canonical backup directory is ~374 MiB; Docker remains 39.33 GiB images + 11.52 GiB build cache + 3.001 GiB volumes; HuggingFace cache is ~20 GiB; llama-swap log is ~21 MiB. These are not deletion authorization.

## 2026-09-21 search/index + inode audit

Mongo diagnostic retention is not actually unbounded: live engine parameters report diagnostic collection enabled with a 250 MB directory ceiling and 10 MB file ceiling. Current LibreChat logical Mongo data is tiny (192 objects / 24 collections; ~53.8 KB data, ~409.6 KB storage, ~995 KB indexes), so the earlier ~118 MB diagnostic observation must not be extrapolated as unbounded annual growth. Meili physical data is ~504 KB; pgvector/Postgres is ~47 MB. These are engine-owned stores: Foundation observes source/index divergence but does not delete their physical files.

File-count observations: Mongo data-node ~201 files; Meili ~9; LibreChat uploads 0; HuggingFace hub ~13; pgvector/Postgres ~1,278. `file_tree_status()` now provides streaming O(depth) observation and symlink exclusion so high file counts do not require `list(...)`-style memory growth.

Exact search ownership readback: Mongo currently has 2 conversations and 6 messages; Meili `convos` and `messages` indexes have exactly 2 and 6 documents respectively. LibreChat's deployed `/app/api/db/indexSync.js` is the Meili synchronization owner and contains native document-deletion plus full/threshold sync behavior. pgvector is not part of that mirror: it contains one LangChain collection row and zero embeddings/dead tuples, so its lifecycle must be tested through the RAG owner separately rather than coupled to chat-history counts.

### MCP development request intake

Source implementation does not demonstrate installed MCP tool availability.

Reviewed development admission reuses the existing owner-private tickets manifest and install lock. `development_admit` accepts only a saved request ID, verifies the private review against that request's instruction SHA and fixed installed root, then reloads the same Guard-bound port. Cancellation does not re-arm an unadmitted request. No automated reviewer or execution grant is created.

Concurrent cancellation of a pending request takes precedence over admission in status, run and delivery, including after process restart when its ticket was already persisted in the manifest. Request closure is checked through an exact WAITING_HUMAN-to-VERIFIED compare-and-swap; cancelled requests cannot be adopted as executable merely because the manifest write completed.
